## 已验证（含证据）

### 1. 安装可靠 —— 真机验证

在飞牛应用中心里用 `trim-cli app install-fpk` **真实安装了 1.6.41**：

    12:05:51 install app gemini2api2 1.6.41
    12:06:45 success
    12:06:45 install_success dirs="[cmd config wizard shares]"

装完的实例：`/health`、登录页、同源画面页 `/vnc/vnc.html` 全部 200。

**这一步骤抓出一个会让所有安装回滚的致命缺陷**：应用中心以应用自己的身份（非 root）运行
生命周期钩子，而该身份不在 `docker` 组里，`docker info` 失败；安装前预检当时把它当阻塞项并
`exit 1`，于是安装被回滚。修法是让预检**只报告不否决**。

### 2. 向导值真的会传进容器

同一次真实安装里，通过向导传入的值可在容器环境变量与挂载点上逐项核对：

    API_KEY      = <向导里填的>
    NEED_API_KEY = no
    HTTPS_PROXY  = <向导里填的代理>
    数据挂载     = <向导里填的目录>/data

这条曾经是**完全失效**的：compose 里写成 `${wizard_port}` 这类形式，而飞牛是按"字段名同名"
注入环境变量、不自动加前缀，于是向导里填的一切被静默丢弃。演练此前也被自己的错误假设骗过
（它导出的正是 `wizard_` 前缀名），现在改为只导出字段名，并用 `docker compose config` +
读容器环境变量双向核对。

### 3. 升级与回滚

`rehearse-upgrade.sh` 走完整三段：装 1.6.40 → 覆盖成 1.6.41 → 再覆盖回 1.6.40，
每段都验证服务能起、`/health` 通、数据标记文件还在。13 项全绿。

> **注意**：回滚**机制**可用，但 1.6.40 **不是安全的回退目标** —— 它的登录画面指向宿主 6080
> 而实际只发布 5920，点「打开登录窗口」会一直空白，加不了账号。索引里该版本已标注已知问题。

### 4. 面板与登录助手对小白可用

- 登录页三步编号、大白话，并预先回答"点不动怎么办"；
- 需要密钥时登录助手也要求口令（口令复用 API 密钥，应用中心入口自动带上，**点进去就用，不用手输**）；
- 报错分情况说人话：`浏览器没在运行，请先点「打开登录窗口」` / `浏览器还在启动，请等几秒再点`；
- 面板正常：`HTTP 200`，标题「Gemini2API - 管理控制台」。

### 5. 加账号链路（到凭据输入为止）

在**真实实例**上验证过：打开登录窗口 → 容器内 Chromium 落在 `gemini.google.com` →
点 `Sign in` → 正确跳转到 `accounts.google.com` 并完整渲染 Google 登录页
（标题 `Sign in - Google Accounts`，有 `Email or phone` 输入框与 `Next` 按钮），
**没有出现"此浏览器不安全"的拦截**。

### 6. 出网自检

容器启动时后台探测两个域名并把结论写进日志，二者**分开判定**：

    [preflight]   OK   gemini.google.com        HTTP 200
    [preflight]   OK   accounts.google.com      HTTP 200

分开是必要的：曾经出现过"gemini 通、accounts 不通"的半瘸状态——服务能用，但点一下加账号会打不开。

### 7. 安全默认值

- 数据目录 700 / 文件 600（账号文件里是明文 Google 会话 Cookie）；
- 鉴权开关 fail-closed：只有明确 `no` 才关鉴权，空值/写错一律按"需要"处理；
- 登录助手的口令只在**校验通过**时才回写下发（早先拒绝页也会把正确口令用 Set-Cookie 发出去）；
- API 密钥不再被写进无需鉴权的前端静态文件；
- 浏览器闲置会自动关闭，并有**绝对存活上限**（否则页面轮询会让闲置判定永不触发）。

## 尚未验证（不要当作已通过）

1. **模型实际产出内容**：账号已建好、接口返回 200 且结构正确，但 Gemini 返回空内容。
   已排除的：账号会话（带 cookie 请求 gemini.google.com/app 返回 200，SNlM0e/cfb2h/FdrFJe
   齐备，页面内有账号邮箱，无地域提示）、模型（四个模型全空，gemini-2.5-flash 也空）、
   协议（OpenAI 与 generateContent 一致）、代理链路（三个域名全 200）。
   **上游自己把它归为已知问题**：v1.6.40 的发布说明（issue #11）原文承认「账号显示 ACTIVE /
   Errors 0 / Models 4，聊天框却只有一句无响应内容」，并说明流式响应一旦发出首字节就把 HTTP
   状态锁成 200，后续失败只能走流内 error 帧，而前端只读 choices[0].delta，于是 503/529/500/400
   长得一模一样。该版本做的是「让面板不再掩盖真实原因」，不是修根因。
   日志原话：Empty response xN (upstream 200, no content)。
2. **卸载钩子的镜像回收在真机上从未生效**：应用中心卸载时会报它自己把 compose 路径
   拼成了绝对路径（open /docker/docker-compose.yaml），钩子没机会运行。卸载本身是
   成功的（见下面第 8 条），但约 1GB 的镜像会留下。钩子现在会如实说明并给出管理员
   该执行的命令，不再声称「可能已清理」。
3. **与本机 curl 的差异**：宿主 shell 经代理访问 Google 一律 000，而容器内同一代理
   访问同一域名返回 200。原因未查明；因为应用跑在容器里，不影响使用，但这条差异没有解释。

### 8. 卸载可靠 —— 真机验证

在一个 appname 不同的测试包上走完整循环（不碰正在使用的实例）：

    安装   -> 版本 1.6.41；向导值进了容器（API_KEY / NEED_API_KEY / HTTPS_PROXY）
    运行   -> 两个容器 healthy；/health 200；登录页 200
    卸载   -> Uninstalled；容器清空、应用中心查不到、应用目录已移除
    卸载后 -> 数据目录保留，里面的标记文件还在（设计如此：卸载不动数据）

应用中心日志：13:02:34 uninstall_start -> 13:02:52 success（18 秒）。

同一条日志里会出现它自己的 stop script error（open /docker/docker-compose.yaml）——
**测试包也一样出现**，所以那是应用中心侧的行为，与本应用配置无关，也不导致卸载失败。

### 9. 加账号与调用链 —— 真机跑通

在真实实例上完整走了一遍：

    打开登录窗口 -> 容器内 Chromium 打开 Google 登录页（无「此浏览器不安全」拦截）
    用户登录成功 -> 浏览器里出现 SID / __Secure-1PSID / APISID / SAPISID
    点「我已完成登录」-> 抓到真实的 psid 与 psidts，建号成功
    /admin/accounts -> total=2 active=2（点两次产生一个重复账号，已删掉重复的那个）
    POST /v1/chat/completions -> HTTP 200，结构正确，usage 里 prompt_tokens 正常计数
    三种协议（OpenAI / Gemini generateContent）行为一致

**唯一没成的是内容为空**，见「尚未验证」第 1 条。上游自己把它归类为
Empty response（HTTP 200 但解析不出内容），并说明单次空响应很常见。

## 已知限制

- 升级上游前必须跑 `check-upstream.sh`，它会核对 11 项依赖（2026-10-26 起核对在树的原生源码，不再是上游镜像）。
- 本仓库为**私有**，应用中心取不到 `fnpack.json`，所以不能用"自定义应用源"安装或升级，
  只能手动装 fpk。
- 登录浏览器是全局单例：同一时间只应有一个登录会话。
- 登录助手的浏览器 profile 不落在卷上：**容器一重建，登录态就没了**，需要重新登录一次。
- **上游依赖 www.google.com**：cookie 重载（POST /admin/reload-cookies）与 token 提取都要访问
  它；该域名不通时重载会失败，PSIDTS 轮换循环不会启动（日志里是 Auto-refresh loop NOT started），
  会话随后变陈旧。代理里必须让 www.google.com 与 accounts.google.com 都可达 —— 实测台湾节点
  会打不开 accounts.google.com，日本/韩国/美国/新加坡节点三个域名都通。
- 代理节点的**名字与真实落地国家不一致**（例如名为「美国节点」的实测出口在韩国），且会变化；
  排障时以实测为准，不要信名字。
